# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

City directory web app for **Žabari** (Braničevo District, Serbia), 12374. Landing page with CTA cards on `/`, lazy-loaded Leaflet satellite map on `/mapa`, per-category module pages (kafići, javne službe, znamenitosti, smeštaj, obrazovanje, plus three "majstor" service categories: vodoinstalater/elektricar/automehanicar), a hidden admin panel, a business-owner dashboard at `/poslovni`, a village-curator dashboard at `/kustos`, a majstor dashboard at `/majstor`, a broadcast service-request page at `/usluge` (users describe a problem + photos, all/selected majstori of a category send counter-offers, accepting one archives the rest), and visitor accounts with favorites/comments/check-ins/reservations. A `/problemi` section lets citizens report communal problems (pothole, fallen tree, illegal dump…) **anonymously** with a photo + map/GPS location, vote on priorities (logged-in only), comment, and browse open/solved reports as a list or pin map. A `/desavanja` feed merges news ("obaveštenja") and events ("događaji") posted by business owners across all villages of the municipality, with a per-village filter and a "Prikaži stara obaveštenja" toggle. A `/naselja` page renders the 15 villages as a Voronoi SVG with per-village facts (population, area, distance, coordinates) and the list of curators assigned to each village. A `/biseri` page ("Zaboravljeni biseri") is a memory map: logged-in users pin scanned old photos to the exact spot they were taken (title, year, village, story, optional present-day shot for a "Nekad/Danas" toggle); submissions land as `pending` and a curator of the photo's village (or admin) approves them from the `/kustos` "Biseri" tab; published biseri are public with likes + flat comments, decade/village filters, photo-frame map pins, and a "Nedavno dodato" grid. UI copy is Serbian (Latin script). Origin: a Claude Design HTML/JSX prototype rebuilt as a real Vite + Fastify stack.

## Commands

All commands run from the repo root (npm workspaces). The DB must be up before any `db:*` or server `dev` script.

```bash
# First-time setup
cp .env.example .env
npm install
npm run db:up          # docker compose up -d db   (uses the `dev` profile)
npm run db:migrate     # creates ~17 tables (idempotent)
npm run db:seed        # 8 categories + 8 starter locations + 15 villages + admin user

# Daily dev (parallel: web :5173, server :3000)
npm run dev

# Single workspace
npm --workspace web    run dev
npm --workspace server run dev
npm --workspace web    run typecheck
npm --workspace web    run build

# DB lifecycle
npm run db:down        # stop container, keep volume
npm run db:reset       # wipe volume, re-migrate, re-seed
```

Default admin is `admin@local` / `admin` — login is by **email**, and the seed derives the email from `ADMIN_USERNAME` (`<username>@local`). Both come from `.env` and are baked into the password hash at seed time, so change them *before* `db:seed` / `db:reset`.

There is no test suite yet.

## Architecture

Two npm workspaces, one Postgres container in dev, a single combined image in prod.

### `server/` — Fastify + Drizzle + postgres-js

- Entry: [server/src/index.ts](server/src/index.ts) — boots migrations (and optionally seed) when `RUN_MIGRATIONS_ON_BOOT` / `RUN_SEED_ON_BOOT` are set, registers JWT + CORS + all route modules, then in production serves the built SPA from `web/dist` with an SPA fallback for non-`/api/*` routes (so React Router deep-links survive a hard refresh).
- Routes (each is a Fastify plugin):
  - [categories.ts](server/src/routes/categories.ts), [locations.ts](server/src/routes/locations.ts) — public list/get + admin-only CRUD on locations (including `village`).
  - [auth.ts](server/src/routes/auth.ts) — bcrypt + JWT register/login + `/api/me` (returns `ownedLocationIds`, `curatedVillages` and `majstorCategories`).
  - [social.ts](server/src/routes/social.ts) — favorites, comments (tree shape, owner-only replies), check-ins.
  - [reservations.ts](server/src/routes/reservations.ts) — visitor-side create/cancel/own-list + public availability windows.
  - [owner.ts](server/src/routes/owner.ts) — `business`-role: list owned locations, edit a restricted field set, approve/decline reservations, list comments on owned objects.
  - [curator.ts](server/src/routes/curator.ts) — `curator`-role: list curated villages and locations in them, POST a draft location (forced `village ∈ curatedVillages`, `status='draft'`), PATCH name/subtitle/address/content (content goes through `mergeCuratorContent` whitelist), list & hide/restore comments in those villages. **No reservations, events, news.**
  - [admin-users.ts](server/src/routes/admin-users.ts) — admin: search users, change role, grant/revoke object ownership, grant/revoke **village curatorship**, grant/revoke **majstor service categories**. The list endpoint exposes `ownedLocations[]`, `curatedVillages[]` and `majstorCategories[]` per row.
  - [usluge.ts](server/src/routes/usluge.ts) — **broadcast service jobs** ("Usluge"): public stats, authed majstor picker, requester-side create/list/accept/cancel (`/api/usluge/*`, `/api/me/usluge`), majstor-side inbox + counter-offer upsert (`/api/majstor/*`, `requireRole('majstor')`). Parallel to (and independent of) the 1-to-1 per-location flow in service-requests.ts. Accept/cancel/offer run in transactions with `SELECT … FOR UPDATE` on the job row — accepting one offer archives all other active offers ("Korisnik je već odabrao drugog majstora."); cancel archives them all. **Contact reveal is acceptance-gated both ways**: the requester sees `majstorPhone` (from `users.phone`, self-set via `PATCH /api/me`) only on the accepted offer; the majstor gets `requesterEmail` + `requesterId` only when HIS offer is accepted. Post-acceptance chat reuses the existing conversations system (`POST /api/conversations` with `recipientId`, no ad) via [StartChat.tsx](web/src/components/StartChat.tsx). **Completion + rating**: either side marks an accepted job done (`PATCH /api/me/usluge/:id` `{action:'complete'}` requester-side, `POST /api/majstor/jobs/:id/complete` majstor-side — only the holder of the accepted offer, guarded `WHERE status='accepted'` in the same FOR-UPDATE transaction pattern); once `completed`, the requester rates via `{action:'rate', stars 1–5, comment ≤160}` which lands on the accepted offer (`rating_stars/rating_comment/rated_at`; re-rate overwrites). Metrics (`avgRating`, `ratingCount`, `completedJobs` = completed jobs whose accepted offer is the majstor's, `avgResponseMinutes` = avg offer-after-job delay) are aggregated by `majstorStats()` and attached to the authed picker AND the **public** `GET /api/majstori` directory (names+ratings+reviews are deliberately public; requester display names appear on reviews like object comments). Text reviews for usluge-majstori are intentionally these short rating comments only — full comments stay object-scoped.
  - [villages.ts](server/src/routes/villages.ts) — public `GET /api/villages` returning facts + curators list per village (no PII — only `id` and `displayName`). Drives `/naselja`.
  - [object-maps.ts](server/src/routes/object-maps.ts) — public floor-plan read + owner write/delete.
  - [events.ts](server/src/routes/events.ts) — public list/single + owner CRUD for timed happenings. Supports `?cat=` and `?village=` filters.
  - [news.ts](server/src/routes/news.ts) — public list/single + owner CRUD for per-object announcements ("obaveštenja"). Slugs auto-generated with anti-collision suffix. Owner POST defaults to `status='published'` with `publishedAt=now`.
  - [newsletter.ts](server/src/routes/newsletter.ts) — `POST /api/newsletter/subscribe` (rate-limited, ON CONFLICT DO NOTHING so success leaks nothing about prior signups).
  - [problemi.ts](server/src/routes/problemi.ts) — **prijava komunalnih problema** ("Problemi"): public list/detail (`GET /api/problemi[?cat&status&village&sort]`, vote/comment counts via correlated subqueries, `X-Total-Count`), **anonymous** create (`POST /api/problemi`, rate limit **5/1h per IP**; `userId` recorded only when a token is present — a logged-in reporter also auto-votes for his own report), authed-only vote toggle (`POST /api/problemi/:id/vote`) and flat comments (`POST /api/problemi/:id/comments`, `official: true` derived from author role admin/curator → "opština" badge). Status flip (`PATCH`, `open ↔ solved` with `solved_at/solved_by`) is allowed for admin, a curator of the problem's village, or the (logged-in) reporter — the detail endpoint returns a computed `canResolve` so the client never needs reporter identity. Admin-only `DELETE` for moderation. Categories are the `PROBLEM_CATEGORIES` enum in [server/src/lib/problemi.ts](server/src/lib/problemi.ts), mirrored (with labels/colors) in [web/src/lib/problemi.ts](web/src/lib/problemi.ts) — edit both together like villages. Coordinates are validated against a rough Žabari bounding box. The **anonymous photo upload** is `POST /api/uploads/problem` in [media.ts](server/src/routes/media.ts) (no auth, own 5/1h IP limit, forced `kind='problem_photo'`, `media.owner_user_id` is NULL for anon uploads); a problem photo becomes publicly readable once a `problems` row references it.
  - [biseri.ts](server/src/routes/biseri.ts) — **"Zaboravljeni biseri"** memory map: public list (`GET /api/biseri[?village]`, published only, like/comment counts via correlated subqueries) and detail (pending/rejected visible only to contributor/admin/curator-of-village), authed create (`POST /api/biseri`, rate limit 10/1h, always `status='pending'`; photo checked for `kind='biser_photo'` + submitter ownership + not-already-referenced), like toggle (`POST /api/biseri/:id/like`) and flat comments — both published-only, moderation (`GET /api/biseri/pending` admin=all / curator=own villages; `PATCH` `published/rejected/pending` gated by the same canModerate; admin-only `DELETE`). The same `PATCH` alternatively accepts `nowPhotoMediaId` (number to set, null to remove) for late-adding the "Danas" shot — allowed to the contributor or a moderator; the detail endpoint returns `canEdit` so the client shows the overlay button on the photo. Validation (year 1850..current, Žabari bbox, story 10–4000) lives in [server/src/lib/biseri.ts](server/src/lib/biseri.ts); web helpers (decades, sepia placeholder, story paragraphs) in [web/src/lib/biseri.ts](web/src/lib/biseri.ts) — the two files are NOT mirrors (unlike villages). Upload is the authed `POST /api/uploads` with `kind='biser_photo'`; a biser photo (either `photo_media_id` or `now_photo_media_id`) becomes publicly readable only while a **published** biser references it; curators of the biser's village can fetch pending photos (AuthImage in the /kustos Biseri tab). `biseri` rows keep `photo_media_id` nullable (seed examples ship photo-less; UI renders a sepia gradient placeholder).
- **Auth helpers** in [server/src/lib/auth.ts](server/src/lib/auth.ts):
  - `requireAuth` — any logged-in user.
  - `requireRole('admin' | 'business' | 'curator')` — admin **always passes** role checks regardless of which role you ask for. Use this for routes that operate on resources scoped per-user.
  - `requireOwner(locationParam)` — admin always passes; otherwise checks `object_owners` for the location id in the named route param.
  - JWT payload is `{ sub, email, role, tv }` (declared via module augmentation on `@fastify/jwt`). The `tv` (token_version) gets bumped on role change / ownership revoke / curator revoke so outstanding sessions are forced to re-auth.
- DB: [schema.ts](server/src/db/schema.ts) holds the Drizzle schema. Per-location content varies a lot per category, so it lives in `module_content.content` (`jsonb`) — no flat columns for menu/rooms/facts. The web module components know how to read each shape. `locations.village` is a nullable text column constrained at the application layer to values in the `SELA_ZABARI` enum (see [server/src/lib/villages.ts](server/src/lib/villages.ts)) — no DB CHECK constraint, the server validates on write. `villages` (per-village facts surfaced on `/naselja`) and `village_curators(user_id, village_name)` carry the curator m-to-m. `news` and `newsletter_subscribers` join the schema; news status is `'draft' | 'pending' | 'published'` with a default of `'pending'` at the column level, but the business POST path sets `'published'` explicitly so direct publishing is the actual default in practice. The `users.role` enum is `'admin' | 'business' | 'user' | 'guest' | 'curator' | 'majstor'` — the CHECK constraint is upgraded idempotently in `migrate.ts`. The "Usluge" tables: `majstor_categories(user_id, category_id)` (grant m-to-m, mirrors `village_curators`; category validated at the app layer against `SERVICE_CATEGORIES` in [server/src/lib/usluge.ts](server/src/lib/usluge.ts), mirrored in [web/src/lib/usluge.ts](web/src/lib/usluge.ts) — edit both together like villages), `service_jobs` (broadcast request: `payload` jsonb `{description, note?, photoIds}`, `target_user_ids` jsonb NULL = all majstori of the category, status `open/accepted/completed/cancelled` + `completed_at/completed_by`, `accepted_offer_id` without FK — set only inside the accept transaction) and `service_offers` (one per majstor per job via UNIQUE, re-send is an upsert; status `active/accepted/archived`; `rating_stars/rating_comment/rated_at` hold the requester's post-completion rating — 1 accepted offer ↔ 1 completed job ↔ ≤1 rating, no separate ratings table). `SERVICE_CATEGORIES` is a superset of the location `MAJSTOR_CATEGORIES` plus service-only `'bela-tehnika'` and `'majstor-za-sve'` (no `categories` row, no map presence). **If a new table references media photoIds, update BOTH the `gcOrphanMedia` keep-set AND the access-control check in [media.ts](server/src/routes/media.ts)** — service_jobs is wired into both (majstor may fetch a photo iff the referencing job is visible to him). The "Problemi" tables: `problems` (anonymous-capable report: `user_id` NULL for anon / ON DELETE SET NULL, app-validated `cat_id` + `village`, `photo_media_id` single photo, status `open/solved` + `solved_at/solved_by`), `problem_votes(problem_id, user_id)` (toggle, PK pair) and `problem_comments` (flat, authed-only). `media.owner_user_id` is **nullable** since the anonymous problem-photo upload landed. The "Biseri" tables: `biseri` (authed submission, `user_id` SET NULL on account delete; `year` + app-validated `village`; `photo_media_id` + optional `now_photo_media_id`, both nullable/SET NULL; status `pending/published/rejected` + `decided_at/decided_by`), `biser_likes(biser_id, user_id)` (toggle, PK pair) and `biser_comments` (flat, authed-only) — biseri is wired into both the `gcOrphanMedia` keep-set and the media access-control check (published → public; pending → contributor/admin/curator-of-village).

### Curator content whitelist

[server/src/lib/locations.ts](server/src/lib/locations.ts) `mergeCuratorContent(catId, oldContent, patch)` is the single source of truth for which `content` keys a curator may write per category. Mirrored on the client in [CuratorLocationEdit.tsx](web/src/pages/CuratorLocationEdit.tsx) `ALLOWED_CONTENT_KEYS` — **edit both together**. Categories:

| catId | curator-editable keys |
| --- | --- |
| `cafe` | `tagline`, `hours`, `contact` (no `menu`) |
| `public` | `tagline`, `hours`, `contact` (no `services`) |
| `landmark` | all keys |
| `hotel` | `tagline`, `contact`, `facts` (no `rooms`) |
| `school` | `tagline`, `contact`, `facts` (no `programs`, no alumni) |
| `vodoinstalater`/`elektricar`/`automehanicar` | `tagline`, `contact`, `note` (no `services`, no `hours`) |

Sending a forbidden key returns HTTP 400 — preferred to silent drop so the client doesn't mask user intent. Allowed keys merge over the existing content, so the forbidden ones survive untouched.
- **Migrations are hand-written DDL** in [migrate.ts](server/src/db/migrate.ts) — no drizzle-kit at runtime. Idempotent (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`). The file also contains a one-shot `DO $$ … $$` block that mirrors any leftover `admin_users` rows into the `users` table with `role='admin'` then drops the legacy table — if you ever rip that block out, do it in a separate commit after confirming all deployed envs are past v1.
- Seed reads from [seed-data.ts](server/src/db/seed-data.ts), which is the **source of truth** for the starter locations (one per category — cafe/public/landmark/hotel/school plus three majstor categories) and their content, plus the 15-row `VILLAGES` array with population (popis 2002), area estimate, distance/direction from Žabari, and coordinates. If you change/expand the dataset, edit that file, then `npm run db:reset`.
- Env: [server/src/env.ts](server/src/env.ts) loads `.env` from the **repo root** (resolved via `import.meta.url`), not the workspace cwd — required because npm workspaces invoke scripts with the workspace as cwd. In Docker the file usually doesn't exist and env comes from compose; `dotenv` silently falls through.

### Reservation conflict logic

[server/src/lib/reservations.ts](server/src/lib/reservations.ts) is where the booking semantics live:

- **Cafés** book a `tableId` for a half-open `tstzrange` `[slotStart, slotEnd)` — overlap check uses Postgres' `&&` operator on `tstzrange(... '[)')`.
- **Hotels** book a `roomKey` for a half-open `daterange` `[dateFrom, dateTo)` (checkout day exclusive) — same pattern with `daterange`.
- `findCafeConflicts` / `findHotelConflicts` accept an optional `excludeId` so the owner-approval path can re-check without flagging the row being approved as its own conflict. **Always re-run conflict checks at approve time** (see [owner.ts](server/src/routes/owner.ts)) — pending requests can race.
- Active statuses for overlap are `pending` and `approved`; `declined`/`cancelled` are ignored.
- `/api/locations/:slug/availability` returns minimal payloads (no `user_id`) so visitor pickers can grey out booked slots without leaking other visitors' identities.

### Background cleanup jobs

Two daily sweeps run from boot (`setInterval` with `unref` so they don't block shutdown), kicked off once immediately so a long-stopped instance doesn't sit on a backlog:

- [guest-cleanup.ts](server/src/lib/guest-cleanup.ts) — deletes `role='guest'` users inactive for >7 days. The 7-day window is the contract surfaced in the GuestBanner UI ("istice za 7 dana neaktivnosti") — change both at once. CASCADE clears favorites/comments/checkins along with the row.
- [desavanja-cleanup.ts](server/src/lib/desavanja-cleanup.ts) — deletes `news` and `events` whose effective end date is more than 30 days old (`COALESCE(published_at, created_at)` for news; `COALESCE(ends_at, starts_at)` for events). The 7-day "hide old" threshold on `/desavanja` is a UI concern only — DB retention is 30 days so admins still have a window to review or backfill.

Both batch deletes 500 rows at a time and loop until a partial batch signals the eligible set is drained.

### Logging

Pino multistream → **stdout + rolling daily files** at `${LOG_DIR}/zabariYYYY-MM-DD.log` (defaults: `/storage/logs` in prod, `./storage/logs` in dev). Retention is `LOG_RETENTION_DAYS` (default 7) — the oldest matching file is unlinked on rotation so the directory never exceeds the window. Rotation is *lazy*: triggered by the first write after a UTC date boundary, so an idle process can't pin an old file handle. Date is UTC-based to avoid the "midnight in Belgrade vs. container TZ" gotcha that could otherwise rotate twice on the same calendar day.

If the file stream can't be opened (missing volume / no perms), the boot warns once and continues with stdout-only — never refuses to start. The implementation lives in [rolling-log.ts](server/src/lib/rolling-log.ts) and the multistream is built in [index.ts](server/src/index.ts) `buildLogger()`. Coolify keeps capturing stdout (so its UI keeps working) and the files persist via the `logs:/storage/logs` volume on `app` in [docker-compose.yml](docker-compose.yml).

Fastify auto-logs every HTTP request. Explicit `req.log.info` lines exist for user-lifecycle events (register, email verification, guest upgrade) in [auth.ts](server/src/routes/auth.ts) — add similar lines if you introduce new domain events worth grep-ing for.

### Floor plans (`object_maps`)

- The layout is a single `jsonb` blob: `{ width, height, items: LayoutItem[] }` where items are `table | room | wall | door`. Tables expose `id` as the bookable key; rooms expose `roomKey`.
- [object-maps.ts](server/src/routes/object-maps.ts) `validateLayout()` is strict — every item needs id/x/y, tables/rooms also need w/h/label/capacity, rooms need a non-empty `roomKey`, and ids must be unique within a layout.
- Saving a new layout **refuses with 422** if any `pending`/`approved` reservation references a `tableId`/`roomKey` that the new layout doesn't contain. Owners must decline/cancel those reservations first.

### Production / Coolify deployment

[Dockerfile](Dockerfile) builds a single image containing both the compiled server and `web/dist`. [docker-compose.yml](docker-compose.yml) has two services:

- `db` — bundled Postgres, **gated by `COMPOSE_PROFILES=dev`**, so it stays inert in production where Coolify supplies a managed Postgres via `DATABASE_URL`.
- `app` — the combined image. In prod `RUN_MIGRATIONS_ON_BOOT=true` (default whenever `NODE_ENV=production`), `RUN_SEED_ON_BOOT` defaults off (flip to `true` only for the very first deploy). Traefik labels expose the app on `${APP_DOMAIN}`. The compose file also attaches `app` to an **external `coolify` network** so it can resolve the managed Postgres's internal hostname — if you rename or remove that network, both Coolify deploys and `docker compose up` will break.

Migrations always run at boot in prod, so schema changes ship with the next image — no separate migrate step.

**Uploads storage.** Uploaded photos bind-mount onto a **Hetzner Volume** (block storage) via a **hardcoded** host path in [docker-compose.yml](docker-compose.yml): `- /mnt/HC_Volume_<ID>/zabari-uploads:/data/uploads`. It is deliberately not an env var — **Coolify does not interpolate `${VAR}` into compose volume sources** (it evaluates the `:-` default at parse time, so an env-driven source silently falls back to a named volume on the root disk; verified via `docker inspect` showing the project-prefixed `..._uploads` named volume even with the env set). Same hardcoded-bind pattern as the logs mount; Coolify surfaces both under Persistent Storage → Directories. The container path (`UPLOAD_DIR`, default `/data/uploads`) and all of [media.ts](server/src/routes/media.ts) are unchanged — the server only ever sees `/data/uploads` and stores relative paths in `media.storage_path`, so swapping the backing store is purely an ops concern. The host dir must be `chown 1000:1000` (the container's `node` user) or uploads fail with `EACCES`. Because storage access is centralized in [media.ts](server/src/routes/media.ts) (relative `storagePath` + `createWriteStream`/`rename`/`createReadStream`), a future move to S3-style object storage would be localized to that one file.

## Conventions worth respecting

- **Slugs are server-side.** [server/src/lib/locations.ts](server/src/lib/locations.ts) / [routes/locations.ts](server/src/routes/locations.ts) slugify Serbian diacritics to ASCII (`č→c`, `š→s`, `ž→z`, `đ→dj`). Don't generate slugs on the client.
- **Drafts.** Admin-created locations land as `status='draft'`. The public list endpoint filters drafts unless `?includeDrafts=1`; the admin list endpoint always returns both.
- **Admin is a superset.** `requireRole('business' | 'curator')` and `requireOwner(...)` short-circuit-pass when `req.user.role === 'admin'`. When adding a new owner- or curator-scoped route, follow the same pattern so admins can act on behalf of either without separate plumbing.
- **Reservation race protection.** Any path that approves a reservation must re-run `findCafeConflicts` / `findHotelConflicts` with `excludeId=row.id`. The initial submit check is not enough — owners may sit on requests for hours.
- **Owner edit scope is intentionally narrow.** `PATCH /api/owner/locations/:id` accepts only `name | subtitle | address | village | content`. Don't widen it to `lat/lng/catId/slug/status` without explicit product approval — those affect the map, the slug URL, and admin draft workflow.
- **Curator edit scope is narrower.** `PATCH /api/curator/locations/:id` accepts only `name | subtitle | address | content` — **no `village`** (curators cannot move a location out of their own scope). `content` goes through `mergeCuratorContent` so disallowed per-category keys (`menu`/`services`/`rooms`/`programs`) are refused with HTTP 400 rather than silently dropped. `POST /api/curator/locations` always lands in `status='draft'` for admin review.
- **Curator role grant/revoke auto-bumps role.** `POST /api/admin/users/:id/grant-curator` promotes a `'user'` to `'curator'` (admin/business untouched); `DELETE` demotes back to `'user'` when the last village grant is removed (admin/business untouched). Mirror of the existing `grant-ownership` flow — copy the pattern when adding new scoped grants. `bumpTokenVersion` runs on every promotion/demotion so outstanding JWTs are invalidated. `grant-majstor`/`grant-majstor/:category` follow the exact same pattern for the `'majstor'` role (promotes only `'user'`, demotes only `'majstor'` — a business/curator user who receives a majstor grant keeps their role and won't see `/majstor`, same documented limitation as curators).
- **Villages are a hardcoded enum, mirrored.** [server/src/lib/villages.ts](server/src/lib/villages.ts) and [web/src/lib/villages.ts](web/src/lib/villages.ts) export `SELA_ZABARI` (the canonical 15 RZS names) as the source of truth, with `isVillage()` exported from both. Backend validates `village` writes against `isVillage()` and returns 400 on unknown values. If you add/remove a village, edit **both** files in the same commit — there's no shared package. The `villages` DB table is keyed on `name`, so renaming a village requires a manual data migration.
- **News/events use `published` as the practical default.** The `news.status` column defaults to `'pending'` at the DB level, but the business POST handler ([news.ts](server/src/routes/news.ts)) and events POST handler both set the row to `'published'` with `publishedAt=now`. Admin moderation is intentionally absent for now — if you reintroduce a moderation step, flip the default at the route layer, not the schema.
- **Comment replies are owner/admin only.** Visitors can only create top-level comments. Enforced in [social.ts](server/src/routes/social.ts) — don't relax this without product input.
- **`includeDrafts=1` is admin-only on the public endpoint.** When adding new list-style endpoints that should hide drafts from the public, mirror that pattern instead of inventing a new one.
- **Adding a new seed dataset on existing prod requires a targeted backfill.** `RUN_SEED_ON_BOOT=false` is the default in prod after the first deploy, so a fresh block added to [seed-data.ts](server/src/db/seed-data.ts) (e.g., the `VILLAGES` array that landed mid-project) WON'T populate on a routine redeploy. Don't flip `RUN_SEED_ON_BOOT=true` for one boot — `runSeed()` also tries to insert demo visitor accounts (`marko@example.com` etc.), demo comments, and demo alumni, none of which belong in prod. Instead write a one-off `INSERT ... ON CONFLICT (...) DO NOTHING` SQL against just the affected table (or a small standalone Node script that imports only the desired const from `seed-data.ts`). The 15-row villages backfill on prod was done exactly this way.
